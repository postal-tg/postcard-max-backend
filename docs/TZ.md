# Техническое задание

## Название проекта

Бот открыток для `MAX`

## Цель

Разработать готовый к деплою сервис, который:

1. Принимает от пользователя текстовую тему.
2. Генерирует по теме открытку.
3. Отправляет результат пользователю в `MAX`.
4. Сохраняет информацию о пользователях, промптах и генерациях.
5. Предоставляет внутреннюю web-панель для просмотра статистики и ошибок.

## Исходные требования

Минимальные требования, полученные по задаче:

1. По промпту генерирует открытку на тему, которую укажет юзер.
2. Собирает информацию о юзерах и промптах.
3. Найти нейронку, которая сможет делать это дешево.

Дополнительное требование от наставника:

- сделать под ключ, в виде готовых к деплою проектов
- оформить новые репозитории в git
- предусмотреть базы и инфраструктуру

## Принятые решения

### Архитектура

Проект разделен на два Python-репозитория:

- `postcard_max_backend`
- `postcard_max_frontend`

### Backend

Назначение:

- прием webhook от `MAX`
- прием update через polling для локальной разработки
- обработка входящих сообщений
- валидация и нормализация промптов
- постановка задач на генерацию в очередь
- интеграция с image provider
- загрузка изображений в storage
- отправка результата обратно в `MAX`
- внутренний API для админки

Стек:

- `FastAPI`
- `PostgreSQL`
- `Redis`
- `Celery`
- `S3-compatible storage`
- `Alembic`

### Frontend

Назначение:

- внутренняя админка для команды
- просмотр пользователей, промптов, генераций, ошибок
- просмотр карточек сущностей
- CSV-экспорт
- прокси-просмотр изображений

Стек:

- `FastAPI`
- `Jinja2`
- `server-rendered HTML`

## Функциональные возможности

### Пользовательская логика

- команда `/start`
- команда `/help`
- отправка темы одним сообщением
- генерация 1 открытки по 1 теме
- callback `Еще вариант`
- callback `Новая тема`

### Работа с текстом

- обработка идет по `message.body.text`
- бизнес-логика не строится на raw-представлении для подсчета длины
- длина темы ограничивается отдельным продуктовым лимитом
- сохраняется исходный текст и нормализованный текст

### Сбор данных

Сохраняются:

- пользователи
- диалоги
- промпты
- генерации
- webhook-события
- ошибки генерации

### Защита и устойчивость

- rate limiting
- ограничение количества активных генераций на пользователя
- blocklist-модерация тем
- retry на внешние вызовы
- readiness healthcheck

## Нейросеть

Базовый провайдер в проекте:

- `OpenAI gpt-image-1-mini`

Архитектурно заложен adapter-подход, чтобы при необходимости заменить провайдера без переписывания бизнес-логики.

## База данных

Используется `PostgreSQL`.

Схема создается миграциями `Alembic`, вручную таблицы создавать не нужно.

Основные таблицы:

- `users`
- `conversations`
- `prompts`
- `generation_requests`
- `webhook_events`

## Что означает “готово к деплою”

В рамках этой задачи это означает:

- проект собран
- зависимости описаны
- БД и инфраструктура предусмотрены
- env-шаблоны есть
- миграции есть
- запуск через Docker описан
- код можно выкладывать на стенд/сервер после подстановки реальных секретов

Это не означает, что проект уже автоматически развернут в production.

## Что требуется для финального запуска

Нужны внешние данные и доступы:

- `MAX_BOT_TOKEN`
- `MAX_BOT_NAME`
- `MAX_BOT_PUBLIC_LINK`
- webhook-данные и доступ к организационному контуру `MAX`
- `OPENAI_API_KEY`
- домен и `HTTPS` для webhook, если запускать через production webhook
